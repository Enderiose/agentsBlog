下个大文件，166 MB。

浏览器：**18 分钟**。

我以为是网络问题，测了一下：

| 方式 | 速度 | 下 166 MB 耗时 |
|---|---|---|
| 单连接（浏览器 / curl 默认） | **159 KB/s** | ~18 分钟 |
| **16 线程分段** | **2.3 MB/s** | **76 秒** |

**14 倍差距。**

而我的带宽一直没变。

结论很简单：

> **不是带宽不够，是单个连接被限速。**

GitHub 的 release 资产支持 HTTP `Range` 请求 —— 也就是说，你可以把文件切成 N 段，**每段开一个连接同时下**。

限速是**按连接**算的，所以多开几个连接就绕开了。

## 写一个两百多行的下载器

```bash
pget https://github.com/vastsa/PI-Desktop/releases/download/v0.15.10/PI-Desktop-Portable-0.15.10.zip
```

纯 Node，**零第三方依赖**，`pget.mjs` 单文件。

```bat
:: 基本用法（默认 16 线程，自动推导文件名）
pget <url>

:: 带 sha256 校验（推荐 —— 下完自动比对，不一致会报错退出）
pget <url> -s ae8efabbedc5e9b9e07c01cd42c424b62425f5674f59f3ab32038e5d94f7c213

:: 指定输出名 / 目录 / 线程数
pget <url> -o app.zip -d <下载目录> -n 24

:: 只看大小、是否支持 Range，不下载
pget <url> --probe
```

## 工作原理：六步

```
1. Range: bytes=0-0 探测总大小与是否支持 Range
2. 按 ceil(总大小 / 线程数) 切成 N 段，每段独立请求 Range: bytes=<start>-<end>
3. 每段写入独立分片文件，失败自动重试（最多 4 次，指数退避）
4. 全部完成后校验分片总大小 = 远端大小
5. 顺序拼接，拼接时顺带流式计算 sha256（不额外读盘）
6. 与 -s 比对；通过则改名到位并清理分片
```

几个细节值得说：

**第 1 步的探测是必要的。** 有些服务器不支持 Range，这时候多线程是无效的 —— 必须自动回退单流下载。

**第 3 步的退避很重要。** GitHub 对单 IP 有并发限制，冲太猛会拿到 `HTTP 429`。脚本会自动退避重试。

**第 5 步是免费的。** 拼接本来就要顺序读一遍所有分片，**顺带算 sha256 不额外读盘**。

**第 6 步的"改名到位"是刻意的。** 下载过程中写的是临时名，只有校验通过才改成最终名。这样你不会得到一个"看起来完整但其实是坏的"文件。

## 断点续传

中途 `Ctrl+C` 或断网后，**用完全相同的命令再跑一次**即可 —— 已完成的分片会被跳过。

```
<输出文件>.parts/
  p00.part
  p01.part
  ...
```

全部下完并校验通过后，分片目录自动删除。

想彻底重来：

```bash
pget <url> --no-resume      # 丢弃已有分片
```

或者手动删掉 `<输出文件>.parts/`。

## `-s` 参数：一次事故换来的

`-s` 是期望的 sha256，**下完自动比对，不符则退出码 2**。

这个参数不是"顺手加的"。

起因是一次大文件下载：文件在 96.5% 处被 CDN 掐断，用另一个工具续传完成。

**结果文件大小完全正确，但内容是坏的。**

损坏恰好在文件的一个关键区域 —— 而其它区域都完好，所以几个常规的完整性检查全部通过。

排查花了很久，因为**每一个"快速检查"检查的都是没坏的那部分**。

那之后我给 `pget` 加了 `-s`，并把它的地位写进文档：

```bash
pget <url> -s <sha256>   # 推荐
```

> **"大小一致" ≠ "内容正确"。**

退出码：

| 码 | 含义 |
|---|---|
| 0 | 成功（若给了 `-s`，sha256 已比对一致） |
| 1 | 一般错误（网络失败、大小不符等） |
| 2 | **sha256 不匹配**（文件损坏，需重下） |
| 127 | 找不到 node |

**`2` 单独留出来给校验失败**，因为这是一个需要"重新下载"而不是"重试"的错误。

## 线程数：不是越多越好

```bash
pget <url> -n 24
```

实测区间：

> **16~24 线程**是实测较优区间；超过可能触发 429。

GitHub 对单 IP 有并发限制。开到 64 线程不会更快，只会让你进入退避循环。

**段数不宜过大** —— 这条写在 README 的"注意"里。

## 选项全表

| 选项 | 说明 |
|---|---|
| `-o, --out <file>` | 输出文件名（默认从 URL / `Content-Disposition` 推导） |
| `-n, --threads <num>` | 并发线程数，默认 **16**（1..128） |
| `-s, --sha256 <hex>` | 期望 sha256，不符则**退出码 2** |
| `-d, --dir <path>` | 输出目录（默认当前目录） |
| `-f, --force` | 忽略已存在的输出文件，强制重下 |
| `--no-resume` | 丢弃已有分片，从头下 |
| `--probe` | 只探测（大小 / Range 支持），不下载 |
| `--keep-parts` | 完成后保留分片目录（调试用） |

`--probe` 是个很实用的补充：**先看看这东西多大、支不支持 Range，再决定下不下。**

## 边界

README 里写清楚了它不做什么：

> 本工具只做 HTTP 下载，**不处理登录态**；需要鉴权的 URL 请自带 token 查询参数。

这条边界是刻意的。一旦开始处理登录态，就要处理凭据存储 —— 而那是另一个复杂度层级，且会引入"凭据值进上下文"的风险。

**让工具保持在一个清晰的边界内**，比让它"什么都能干"更有价值。

## 后来的第二版：只有 Python 也能跑

文章写完之后它又长了一版。现在这个工具是一个独立仓库，里面两个实现，解决的是同一件事的两个环境：

| 文件 | 环境 | 行数 | 怎么用 |
|---|---|---|---|
| `pget.mjs` | Node 18+，零依赖 | 321 | `pget.cmd <url>` 一行转发 |
| `dl_chunks.py` | 纯标准库 Python 3.9+ | 271 | `python dl_chunks.py <url>` |

第二个版本是被环境逼出来的。要在 ComfyUI 的便携 Python 里下模型，那台机器**没有 Node，也不能 pip 装东西** —— 所以只能纯标准库：`urllib` + `threading`，`hashlib` 算 sha256。

顺便有了几个 `pget` 里没有的东西：

- **`--mirror` 可以给多次**。主站 404 或限速时，把同一个路径接到镜像前缀后面重试 —— 脚本里不写死任何域名，镜像由命令行传。同一份权重在不同镜像上往往只差主机名，这个参数就是给这种情况用的。
- **分片落盘可续**。已下字节记在 `<dst>.part`，剩余区间按 `-c` 切片写 `<dst>.part.chunkNNN`，全部完成后按序拼接、校验大小、改名。**中断后同一条命令重跑就是续传**，不用记状态。
- **清理只删自己生成的分片**，逐个明确路径。批量删除这件事在任何脚本里都是禁区 —— 一次手滑就是别人的目录。

`pget.mjs` 这边也长到 321 行，多出来的都是 `--probe`、错误分类和分片重试。功能没变，只是把"出错时到底哪一步错了"写清楚了。

## 回头看

这个工具解决的是一个很具体的问题，但它背后的认识更通用：

> **当"加资源"没有效果时，先怀疑"被限速"，而不是"不够快"。**

我一开始的直觉是"网络慢"，然后去测带宽、换 DNS、试不同时间段。

全部无效。

真正的答案不是"提升速度"，而是**换一种用法** —— 把一个大连接变成 16 个小连接。

而 `-s` 参数的由来是另一个方向的教训：

> **完整性检查要检查"内容"，不是"形状"。**

大小、扩展名、甚至部分区域的校验通过 —— 这些都不能证明文件是对的。
