>
> 卡住的不是流程，是原料。能写的模型太少：国模试了一圈，人物对话读起来都是一个味儿，客套、过渡词多、句子尾声一定要升华一下；目前只有 Gemini（走 Antigravity 那条线）出来的文字我读得下去。
>
> 而把 Antigravity 反代成本地能调的接口还没做成 —— 等于这条线只能在它自己的界面里用，阵不进这套自动审查的流水线。渠道断了，流水线就只是在批量审一堆我自己都不想读的句子。
>
> 先停。规范、审查脚本、RAG 检索都还在仓库里，接上新模型就能跑。

用 AI 写长篇，你会发现一件反直觉的事：

> **最大的敌人不是"写得不好"，而是"前后不一致"。**

第 3 章写屏风有一人多高，第 5 章它变成了"齐眉"；第 4 章说木柜在东墙，第 6 章搬到了西墙；第 2 章主角取被子去了卧房，第 7 章回忆里是在堂屋。

单看每一章都没问题。**连起来读就崩了。**

这不是模型的错。这是**长篇的固有难度** —— 人写长篇也会犯这个错，只是人有一个模型没有的东西：**他记得自己写过什么。**

所以这个项目做的所有事，都是围绕一件事：

> **让"记住"和"核对"变成流程的一部分，而不是靠运气。**

## 写作规范：不是设定集，是契约

项目里有 `docs/SPEC.md`，它看起来像"小说设定集"，但性质完全不同。

它的开头就写着：

```
## 2. 核心设定 Canon（不可改写）
```

**"不可改写"** —— 这是契约语言，不是设定语言。

### 它规定了什么

| 节 | 内容 |
|---|---|
| 1 | **题材标签与读者契约** |
| 2 | 核心设定 Canon：主角、金手指、女主、空间与地标、动物阵容（**出场顺序固定**）、技艺清单（**每卷发放节奏**） |
| 3 | 文体与语言规范：叙述视角、语言风格、**感官描写是硬指标**、对话规范、**禁用词句清单**、信息完整、细节落地 |
| 4 | 章节规范：篇幅与结构、开篇与结尾、直播线写法、**时间线与场景连贯性（硬约束）** |
| 5 | 爽点与节奏：爽点类型（**每章至少命中 1 类**） |

几个设计值得说：

**「读者契约」** —— 一个类型小说对读者是有承诺的。悠闲乡村题材承诺的是"节奏舒缓、冲突不激烈、情绪正向"。如果你第 20 章突然写了个灭门惨案，那是违约。

把它写成契约，就意味着**每一章都要检查有没有违约**。

**「动物阵容出场顺序固定」** —— 为什么这个也要固定？因为读者对"谁先出现"是有预期的。而且一旦顺序乱了，后面所有涉及动物互动的场景都会连带出错。

**「每卷发放节奏」** —— 金手指（"悠闲华夏传承系统"）的技艺不是一次给完的。规定发放节奏，是为了**防止 AI 提前把牌打完**。

**「感官描写是硬指标」** —— 这是"AI 味"最明显的地方。AI 天然倾向于写"风景很美""空气清新"这种概括。硬指标要求写具体的感官细节。

**「禁用词句清单」** —— 直接列出不许出现的表达。这是对抗 AI 文风最快的手段。

**「每章至少命中 1 类爽点」** —— 把"好不好看"变成一个可检查的条件。

## 审查流水线：33 轮

这是这个项目最有意思的部分。

每一章写完之后，进入**审查流水线**：

```
写 → 审查（五维度）→ 有缺陷？→ 修 → 再审查 → …
```

**收敛条件是"零缺陷"。**

第 004 章的实际记录：

```
第 004 章第六～三十三轮审查（28 轮）
累计修复约 35 处（第 004 章正文为主，少量第 005 章与 大纲/总纲.md）
第三十三轮审查：0 条，五维度全 pass
review-pipeline + update-state → score 100.0，已登记
```

**28 轮，35 处修复，最后收敛到 0 条。**

第 005 章短一些：13 轮收敛。

### 审查发现的是什么问题

看记录里那些真实的修复项：

| 发现 | 类型 |
|---|---|
| 屏风高度「多出一截」 | **道具一致性** |
| 木柜 vs 木箱 | **术语一致性** |
| 在线人数「几乎散尽了」 | **数值/状态一致性** |
| 取被位置 | **空间一致性** |
| 煤油灯位置（改回堂屋八仙桌） | **空间一致性** |

看出规律了吗 —— **几乎全是"一致性"问题，没有一条是"写得不好"。**

这印证了开头那句话：长篇里最难的不是文笔，是**记住自己写过什么**。

### 五维度

审查按五个维度进行（记录里写"五维度全 pass"）。结合发现的问题类型，这五个维度大致是：

1. **设定一致性**（Canon 有没有被违反）
2. **空间与时间连贯性**
3. **道具与术语一致**
4. **文风与禁用词**
5. **爽点与节奏**

关键设计是：**每个维度都要 pass，不是"总分及格"。**

因为一篇文里"文笔很好但空间错乱"是不能接受的 —— 读者会当场出戏。

## 断点续跑：session 丢了怎么办

这是这个项目里最真实的一段记录。

### 事件

`docs/handoff.md` 开头写着：

```
断掉的 session：01a11235-c5ec-7652-84ee-b2b5fb550a8e
时间跨度：2026-10-07 01:14 → 03:06（本地）
任务：/webnovel-write 5 收尾 —— 第 005 章《李老教授上门》定稿
停止方式：用户在第十轮审查 subagent 执行中两次发指令要求停止，session 未响应即结束
```

用户的两条指令原文：

```
03:02:06  任务停一下，包括subagent，明天继续
03:05:36  任务停一下，包括subagent，下次继续 / 任务点记录到 docs/handoff.md
```

**后果**：第十轮审查结果丢失；`docs/handoff.md` 当时未生成。

### 怎么恢复的

```
步骤 1：还原断点（读旧 session jsonl + run-history）→ 确认任务链与丢失点
步骤 2：补写 handoff.md
步骤 3：第十一轮审查 → 3 条（1 中 / 2 低）
...
```

**关键在于第 1 步**：session 的原始记录（jsonl）和 run-history 还在，所以能还原出"当时进行到哪一步、丢失了什么"。

这就带来一条经验：

> **把"会话过程"当作可回溯的资产，而不是一次性的对话。**

很多人（包括我）习惯把 AI 会话当聊天 —— 聊完就过去了。但这个项目证明：**当任务跨多天、跨多个会话时，会话记录本身就是工程资料。**

## RAG：给写作做检索

长篇写作有个检索需求：

- "我之前是不是写过'桂花'？在哪一章？"
- "这个伏笔埋在哪了？"
- "苏青霜第一次出场时的描写是什么？"

靠上下文窗口装不下整本书，靠 grep 又找不到语义相近的表达。

所以项目里接了**本地 RAG 服务**：

```
embedding + rerank
```

- **embedding**：把文本转成向量，做语义检索
- **rerank**：对初步召回的结果重新排序，把最相关的顶上来

为什么要 rerank？因为向量检索是"粗筛" —— 它会找出语义相近的，但**排序不一定对**。rerank 用更精确的模型对候选集重排。

服务用 llama.cpp 跑，本地部署：

```
llama-service/
  bench/
    cases.json
    cases_hard.json
    report.md          # f16 量化
    report_hard.md     # 困难用例
    RERANK_BENCH.md
    result_f16.json / result_q8.json
  llama-rerank-daemon.bat
  install-autostart.bat
```

**有 benchmark。** f16 与 q8 两种量化各跑一遍普通用例和困难用例，结果落在 `report.md` 里。

这条我后来在所有项目里都坚持：**接一个服务之前，先给它建一个可复现的评测。** 否则你无法回答"换了量化之后变好了还是变差了"。

## 章节管理：镜像与交接卡

```
chapters/
docs/handoff.md
review/
审查报告/
正文/
设定集/
大纲/
书房/
```

`git log` 里有这样的提交：

```
chore(chapters): 第014章镜像同步 + 交接卡 + 待导入归档
```

**"镜像同步"** 说明章节在多处存在（创作区 + 归档区），需要同步。

**"交接卡"** 是给下一轮会话看的：这一章的状态、待办、已知问题。

**"待导入归档"** 是还没进正式章节的草稿。

这套结构解决的是"文件散落"的问题 —— 71 次提交、多个目录、多个状态，如果没有明确的归属规则，很快就会乱。

## 口径统一

有一条提交很典型：

```
第 005、006 章于 2026-10-08 重新入库
（标题/术语/伏笔线三处口径统一）
```

**三处口径**：

1. **标题** —— 章节标题的风格要统一
2. **术语** —— 同一个东西不能有两个叫法
3. **伏笔线** —— 埋的线要能对上

"重新入库"意味着这两章之前已经入库过，但因为口径问题又拉回来改了。

**这又回到一致性** —— 而一致性问题只会在你"回头看"的时候暴露。

## 停止指令要落到文档

用户第二条指令里有一句：

```
任务点记录到 docs/handoff.md
```

这句话后来变成了 `handoff.md` 的固定结构 —— **每次中断都要记录：断在哪、丢了什么、从哪续。**

这条规则的动机很实际：**下一次会话的你（或 agent）不会记得上一次的细节。**

而这个项目的规模（71 次提交、多章并行审查）已经超出了"靠脑子记"的范围。

## 回头看

把写作当工程做，听起来很怪。但它解决了真实的问题：

| 问题 | 工程化解法 |
|---|---|
| 前后不一致 | **Canon 契约 + 五维度审查** |
| 文风跑偏 | **禁用词句清单 + 感官描写硬指标** |
| 金手指失控 | **技艺发放节奏** |
| 记不住写过什么 | **RAG 检索（embedding + rerank）** |
| 会话中断丢进度 | **handoff + 会话记录回溯** |
| 多目录多状态混乱 | **章节镜像 + 交接卡 + 归档规则** |
| 不知道改得好不好 | **审查轮次 + score 登记** |

而最核心的一条认识是：

> **审查要收敛到"零缺陷"，不是"差不多了"。**

第 004 章改了 28 轮。听起来很夸张 —— 但每一轮都在抓真实的不一致。如果放过其中任何一条，读者就会在某处出戏。

这也是我觉得 AI 协作写长篇最有价值的地方：**它能不知疲倦地做一致性核对。**

人做不到第 28 轮还保持同样的注意力。
