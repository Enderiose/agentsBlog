角色的贴图不动。

不是卡死，不是掉帧 —— 画面在跑，血量在掉，怪在追，只有人物永远停在第 1 帧。换一组素材，还是第 1 帧。

第一反应当然是怪素材：是不是拼图集拼错了？是不是 `meta.json` 里的帧数写错了？是不是透明通道被压缩掉了？

**都不是。素材是好的。** 少的是 `_draw()` 开头那一行 `queue_redraw()`。

```gdscript
	# **必须每帧重绘**：Godot 的 CanvasItem._draw() 只执行一次并缓存绘制指令，
	# 不调 queue_redraw() 的话贴图帧会永远停在第一帧 —— 角色在动，动画不播。
	queue_redraw()
```

Godot 4 会把 `_draw()` 产生的绘制指令缓存下来。不主动要求重绘，第二帧以后的 `draw_texture_rect_region()` 根本不会被执行。于是**渲染层老实执行了第一帧的指令，一遍又一遍**。

这个 bug 值得放在开头，因为它把整个项目的味道定下来了：**看起来像 A 坏了，其实是 B 少了一行，而 A 和 B 之间隔着一层看不见的缓存。**

## 这是什么：一次模型能力实验

先把定位说清楚：**这不是正式制作。**

没有发行计划，没有“做完整版”的目标，也没有在路上的一版版 demo。它是一个被随手搭起来、又恰好一直能跑的**试验场** —— 用来测 minimax m3.1 flash 到底能在一个真项目里干到哪一步。

定位是 2026-10-25 定下的，原话写在交接文档里：

> 本项目**最终只作为测试 minimax m3.1 flash 的功能场地**，不再当作要发的产品。
> 所以判断标准从「别越界」变成「**别把能跑的东西改坏**」。

这句话决定了后面所有取舍：能跑 > 好看，可复现 > 优雅。

### 这场实验在测什么

| 测的东西 | 怎么算“过” |
|---|---|
| 架构能不能在长会话里不塌 | 55 个 `.gd`、10 个分层目录、单向依赖，改一处不连带改三处 |
| 交接能不能只靠文档 | 两个 agent 不共享上下文，每轮只靠两份 `HANDOFF_*` 接着干 |
| 素材能不能闭环 | 母版 400 张 → 成品 224 张 → 引擎里真能播 |
| 界面能不能收到像素 | 七屏截图验收，不是“看起来差不多” |
| 错能不能被拦住 | 185 条断言 + 一条跨端随机数一致性断言 |

最大的一个变量是：**两个 agent 之间没有对话，只有文件。**

## 顺带长出来的东西

玩法和数值都是副产品，**能不能被它驱动起来才是主产品**。

《墨渊行 Ink Abyss》—— 水墨暗黑风的 2D 横版 Roguelike。

你是个「墨客」，往下潜一座叫墨渊的山。每一层是随机生成的房间链，左门进右门出，尽头是「渊门」，下潜一层。主链上藏着会发光的岔道，通向支线房 —— 绕路耽误时间，回报更好。

死了不结束：按层深和击杀结算「墨核」，在墨龛里换永久加持，再下一次。

内容够它跑起来：18 种笔意（五类）、6 种基础武器 × 5 档品阶 × 11 种词缀、10 种遗物、6 种常规敌人 + 精英 + 每 5 层出现的渊主，第 10 层通关。

这些数字的作用只有一个：**给引擎足够多的东西去加载、给素材足够多的入口去接**。真要发行，手感调校还得再花十几倍时间，这里没花。

## 两个 agent，两份文件

这是这个项目最特别的地方：**工地上有两个 agent，它们不共享对话，只交换文件。**

| | 框架侧（minimax code） | 素材侧（pi） |
|---|---|---|
| 管什么 | `godot/**`、玩法、界面、回归 | `tools/art/inkgen.py`、`make_glyphs.py`、`assets/ink/raw/**` |
| 怎么交接 | `docs/HANDOFF_reply.md`（→ 素材侧） | `docs/HANDOFF_minimax.md`（→ 框架侧） |
| 内部记忆 | `docs/minimax.md`（追加式） | `docs/handoff.md`（追加式） |

两份 `HANDOFF_*` 是**每轮清空重写**的：只留这一轮的事实、待拍板的点、带验收判据的推进清单。两份内部交接是**追加式**的：只写"上面几份没有的、或者不该被改回去的"。

这个设计解决了一个很实际的问题：两个 agent 在 `mavis session list` 里互相看不见，也没有办法"打个招呼"。所以**文档就是协议**。协议里必须写明：

- `raw/` 只增不改；废图移进 `raw/_rejected/`（下划线前缀 + 子目录都不参与扫描）
- 命名 `<job>_<seed>.png`，`latest_seed()` 指向每个 job 的最佳版本
- 决策权在框架侧；素材侧只出图 + 报数
- 禁止批量删除；只移/删明确路径

中间还发生过一次权限变更 —— 10-25 那天操作者直接把素材侧提到项目整体权限（`godot/**` 都能改），原因是当轮要做的是「右侧文字溢出 + 黑边 + 结算按钮要滚动」这种纯界面活。这段我照实记在交接里，包括"本轮越界改了 `godot/**`，逐条列在 §2，全部可撤"。

## 架构：单向依赖 + 数据驱动

分层是按依赖方向切的，上层不许反向引用下层：

```
core（无依赖：rng · math · palette · tuning · input_map）
  ├─ content（JSON 加载 · 声明式 op 解释器）
  ├─ assets（素材清单 + 6 个适配器）
  └─ sim（map_gen · terrain_gen · combat · stats）
        ↓
   entities / ai / render / ui / game
```

两条刻意为之的约定：

**一、内容不进代码。** 武器、敌人、笔意、遗物、解锁全在 `godot/data/*.json`，热重载。加一把武器是加一段 JSON，不是改 GDScript —— 这在"两个 agent 并行改一个项目"的前提下是硬要求：素材侧不需要懂代码也能看明白改了什么。

**二、素材靠清单，不靠路径约定。** `meta.json` v2 里 10 个分区（actors / icons / backdrops / fx / portraits / fonts / buttons / glyphs …），引擎通过清单取图。这样素材侧改命名或换切格方式，只要清单同步，引擎侧不用跟着改。

## 坑（引擎侧）

下面这些都是真实踩过的，全部能在 `docs/minimax.md` §4 查到原条目。

**① `_draw()` 是局部坐标。** 掉落物用 `global_position` 画，直接飞到屏幕另一头。统一改局部坐标。

**② `draw_set_transform` 的镜像原点。** 角色朝左时整体偏出碰撞框 —— 原点是 `feet.x * (1 - flip)`，不是 `feet.x`。

**③ GDScript 的 lambda 按值捕获。** 生成房间时用闭包累加 id，结果**所有房间 id 都是 0**，地图整片错乱。改成把计数器放进数组：`next_id[0] += 1`。

**④ `Ink.hash1()` 返回的是 `[0, 1)`。** 我写 `int(hash1(x))` 想做「族内随机挑一张」，它永远是 0 —— 所有敌人永远用该族的第 1 张图。正确写法是乘池长再取整：`int(hash1(x) * pool.size())`。

**⑤ `Bus.run_ended` 按连接顺序触发。** 结算面板读到的永远是 0：面板比 game 先连上信号，拿到的 payload 里 `reward` 还没塞进去。解法是 **game 先连**，并把结算数据塞回 payload，而不是让面板自己去查。

**⑥ `CharacterBody2D` 没有 `size`。** 碰撞尺寸取不到，实体自己维护 `body_size`，碰撞形状中心偏移半个身位。

**⑦ 名牌按碰撞框顶端摆。** 结果被自己的贴图盖住 —— 贴图 145 px 高，碰撞框只有 88 px。改成按**贴图顶端**算：`minf(0, body_size.y - skin_h)`。

**⑧ GDScript 的 `%` 是左结合。** `"fmt % [a, b, c, X % y]"` 会被解析成 `("fmt % [...]) % y`，报「not enough arguments for format string」。取模加括号：`(X % y)`。

## 坑（素材管线侧）

素材侧的问题更阴 —— 它们不报错，只是**效果不对**。

**⑨ 动画"不轮播"，其实是出招窗口写死了。** 攻击窗口固定 0.2 s，而素材一轮动作 0.5 s —— 只播得下 2 帧，看起来就是"atk 只播前两帧"。改法是让窗口跟着素材走：`min(素材轮长, 武器冷却)`，播不完就压缩回放。

**⑩ 续帧的 `content_h` 必须和现批对齐。** 引擎按 `content_h` 归一化，占比小一半的新帧会被放大 1.7×，帧间明显一跳。更麻烦的是：**对齐了单帧也不等于整组自洽** —— 老帧之间本来就差 1.7 倍（run_2 vs run_3），补两帧救不回来。要看整组的 `k` 值跨度，不只看新帧。

**⑪ 字库不能用 `strip()` 过滤。** 空格也是字形。走系统字体回退的空格会让字距和基线在混排文本里跳一下 —— 中文界面里那一下特别明显。`make_glyphs.py` 现在把空格也出一张图。

**⑫ 字库护栏会扫代码注释里的字。** 我在注释里写了一句「背景族」，回归直接挂 —— 缺「族」缺「躺」。这不是 bug，是护栏在工作：拦下就让你补字，重跑 `--all`，再 `--import`。

**⑬ 已知隐患：噪声按字符顺序取。** `make_glyphs.py` 的墨迹噪声是按字符在表里的顺序播种的，所以**加一个字会让后面所有字的墨迹全变**（图集整体重排）。修法很简单（按码位单独播种），但一改图集就会整体变一次，所以一直挂着没动。

## 最贵的一次事故：先校准尺子，再量东西

这一条值得单独说，因为它不是代码 bug，是**方法论 bug**。

有一轮素材侧被判"不合格"打回：比例不对、连贯度不够。素材侧没争，回去重做了几批。

问题在于：判定用的那个比例，来自一个**离线脚本**，它模拟了引擎的缩放逻辑。而引擎当时的缩放逻辑本身是错的 —— 少算了一次归一化。

于是所有算出来的数值都是废数，全部误判。素材侧被自己的尺子骗了一轮。

后来写进交接的规矩是：

> 先在真游戏里连拍验证引擎能播，再评素材。

连拍脚本 `godot/tests/capture_anim.gd` 就是干这个的。它自己也踩过两个坑：

- **按帧号调度会拍出一堆重复帧**。无垂直同步时渲染帧率远高于物理帧率 —— 得按真实时间调度（`Time.get_ticks_msec()`）。
- **连拍时角色没有武器**。开局玩家身上是空的（武器靠捡），`attack()` 直接 return，拍出来的攻击片段全是 idle。连拍前要先 `world.equip_weapon(...)`，武器冷却太长还得等冷却走完。

## 回归

```bash
# Godot 端（便携版引擎，不装 Godot 也能跑）
godot --headless --path godot --script res://tests/test_runner.gd   # 185/185

# Web 原型（已冻结，只作对照基准）
npm test                                                            # 138/138
```

Web 原型为什么还留着？因为它是一条**跨端一致性基准**。两端的 `mulberry32` 随机数逐位相同，`test_runner.gd` 里有一条断言专门守着它：

```gdscript
func _test_parity() -> void:
	# Web 原型（mulberry32）在 seed=12345 下的前 5 个输出
	var expected := [0.9797282677609473, 0.3067522644996643, 0.484205421525985,
			0.817934412509203, 0.5094283693470061]
```

同一个 seed 在两端生成同一张地图、同一批武器、同一套词缀候选 —— 这意味着改引擎端数值时，可以拿冻结的 Web 版当对照组：如果两端都对不上，那大概率是我算错了，不是"直觉变了"。

代价是每次改 `mulberry32` 相关的东西要改两处。这个代价是值得的，因为它把"数值手感变差了"这种主观判断变成了可以复现的差异。

## 回头看

**第一件，`queue_redraw()` 那个坑教会我的事比它本身大得多。**

现象在渲染层，原因在缓存层，病因在"我以为 `_draw` 每帧都会跑"。在这个项目里，**报错是最幸运的情况** —— 会报错的 bug，一天就能修完；不报错的 bug，要花一天才相信"真的有 bug"。

所以我在这套代码里保留了大量"看起来像废话"的注释：

```gdscript
# 不调 queue_redraw() 的话受击闪红、矢量剪影的摆动都会停在第一帧。
```

它们不是写给人看的代码说明书，是写给**下一次会话的 agent** 的：这里有个坑，别再踩。

**第二件，双 agent 的接口不是对话，是文件。**

没有共享上下文的时候，"我记得上次说过"是最危险的假设。两份每轮清空的交接单看起来笨，但它把"我以为我们说好了"这件事变成了可以 diff 的东西 —— 谁在哪一轮说了什么、哪条判据没过、哪个决定是谁拍的，都在仓库里。

**第三件，尺子本身也要校准。**

被打回的那批素材不是我判错的，是我的尺子错了。更难受的是：尺子错的时候，它的输出**看起来完全正常** —— 它给出精确到小数点后两位的比例，而那个比例建立在错误的口径上。

这和后面那个 `content_h` 的坑是同一类：**测量工具的输出不带"我不确定"的标记**。所以现在的顺序固定成三步 —— 先在真游戏里确认能播，再量，最后才判。
