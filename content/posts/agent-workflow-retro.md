`AO_AccountOverview` 的 321 次提交里，没有一次是因为「AI 写错了符号」而进到游戏里才发现。

这不是因为模型强，而是因为我在第一周就撞上了一个问题：

> **我记不住这个项目了。**

3.4 万行 Lua，五个设置页文件，17 条红线，270 个 i18n 键。每次新开会话，我要花很长时间重新解释「这个项目是什么、规矩是什么、上次卡在哪」。

这篇记录我最后是怎么解决的。

## 一、AGENTS.md 是索引，不是文档

一开始我把所有东西都塞进 `AGENTS.md`，它膨胀到没法读。

后来定了个结构：

```
AGENTS.md  ← 索引 + 红线摘要 + 踩坑记录（14KB，必须短）
docs/
├── SPEC.md      项目地图（加载顺序、数据模型、事件流、列预算、17 条红线）
├── PLAN.md      功能排期（已排期 / 已否决）
├── DEV.md       操作手册（闸门判据、编码约定、i18n 工作流）
├── CHANGELOG.md 上游同步记录
└── handoff.md   会话交接
```

`AGENTS.md` 里有一节是硬性要求：

> **§9 踩过的坑**
> 踩过的坑每次都要更新在这里，简洁明了的总结，不易长篇大论。

**「不易长篇大论」这五个字是关键。** 一个没人读的坑记录，等于没有记录。

规则是：`AGENTS.md` 只放「下一轮必须知道的东西」，细节全部下沉到 `docs/`。所以 §9 里每条坑都是三五行讲完，需要展开的地方留一句「详 `docs/DEV.md` §xxx」。

## 二、handoff.md：会话之间的桥

Agent 会话会结束，项目不会。`handoff.md` 是这两者之间的桥。

它经历过两次大幅压缩，提交记录里留着痕迹：

```
docs(handoff): 压缩 223→93 行（旧版在 997255a）
    —— 删项逐条核过已在 SPEC/PLAN/AGENTS/DEV，只留两扇窗口径、本轮细节与查过的 API 结论

docs: handoff 压缩 518 → 110 行
    （按头部声明去掉与 SPEC/PLAN 的重复）+ 规则补压缩例外
```

**为什么压缩这么重要**：交接文档越长，下一轮会话越不愿意读；越不读，越会重复问已经写过的东西；重复写又让它更长。这是个正反馈的死循环。

压缩的判据是：**这条信息在别处已经有了吗？** 如果有，删掉，留指针。

所以 `handoff.md` 的内容收敛成三类：

1. **只在这轮有效的** —— 本 session 干了什么、卡在哪
2. **还没落地的结论** —— 查过的 API 结论、待定的形态 A/B
3. **两扇窗之类的口径** —— 跨文件、容易漏、值得反复看

## 三、子代理：禁止猜测，必须查证

`.pi/agents/` 下三个只读子代理：

| 代理 | 职责 | 验收 |
|---|---|---|
| `ao-code` | 本仓库代码检索：「X 在哪 / 谁调用 X / X 字段被谁读写 / 走什么口径」 | 结论自带 `file:line` 证据 |
| `wow-api` | WoW API 查询 | 必须给出来源 |
| `wowdata` | 游戏数据（Spell / Item / Creature） | 必须给出来源 |

核心约定写死在 `AGENTS.md` 的「外部查询」一节：

> **禁止猜测，必须查证。**

为什么这条这么重要？因为 Agent 最擅长的恰恰是**看起来合理的猜测**。

一个例子：我让它查 `GetFriendshipReputation` 的返回结构。它给的答案「看起来对」—— 直到我发现 MoP Classic 5.5.4 **根本没有这个裸全局**，只有 `C_GossipInfo.GetFriendshipReputation`，而且返回类型还不一样（表 vs 多值）。

只探裸全局的写法**不报错，只是整段静默短路**。比崩溃更难发现。

所以子代理的验收条件里必须带**证据要求**。`ao-code` 的定义里写得很明确：

```
acceptance: { level: "none", reason: "只读代码检索，结论自带 file:line 证据" }
acceptanceRole: read-only
```

**只读**这一点也是刻意的。检索型子代理不应该有写权限 —— 它的价值在于给结论，不在于动手。

## 四、子代理定义本身也踩坑

`.pi/agents/*.md` 的 frontmatter 里，有两个字段会**直接顶掉启动**：

```yaml
thinking: low     # → 被拼成「模型:low」
async: false      # → 前台子代理不加载 ambient 扩展，自定义 provider 解析不到
```

两者的报错都是 `Model not found`，看起来像模型表坏了。

**删掉字段就好。**

验「有没有被发现」的正确方式：

```
subagent({ action: "list", capabilities: true })
```

不要靠猜。这条也写进了 §9。

## 五、文档会漂移，而且必须主动清

文档写了就会过期。`git log` 里有一串专门清漂移的提交：

```
docs(漂移): 清掉指向已删文件与已不存在章节的残链（6 文件 +15/-12）
docs(工作流): 收口 PLAN/SPEC 漂移 + prompt/ 提级 T0 迁 .pi/prompts + 登记 T11
docs(T11): 修正过期留痕声明 —— weekly-matrix 分支已不存在、f199475 无引用
docs(titan): 1.1.1 拍板不同步 —— titan 副本停在 1.1.0 记为有意偏移，禁止自动抄齐
```

最后一条特别值得说：**「有意偏移」也要写下来**。

两个客户端副本版本不一致，如果不记录原因，下一个 Agent 会「顺手抄齐」—— 而这恰恰是错的。

所以文档不只是记「是什么」，还要记 **「为什么不是另一个样子」**。后者才是 Agent 最容易搞错的部分。

## 六、否决也要留痕

`PLAN.md` 里有一节叫 **§已否决**。

「周常矩阵」功能做完一版才发现它就是概览的转置，撤销了。但记录没有删：

> 功能已撤销。实现曾在分支 `feat/weekly-matrix`，但该分支本地与远端已不存在、commit 无引用 → 代码当作已放弃，**别再去找它，要重做就从零设计**。

这段文字的价值在于：它同时告诉下一轮「别找那个分支」和「为什么不能做」。

不写「已否决」，Agent 会重新提出同一个方案 —— 而且会很有信心。

## 七、Session 工作流

最后固化下来的流程：

### 启动
读 `AGENTS.md` → 读 `docs/handoff.md` → 需要细节时读 `SPEC.md` / `PLAN.md`

### 执行
改代码 → 跑 `node tools\gates.js` → 需要外部信息时派子代理 → **禁止猜测**

### 结束
更新 `handoff.md` → 新踩的坑进 `AGENTS.md` §9 → 口径变化同步 `SPEC.md`

三条结束动作里，**「新踩的坑进 §9」是最容易漏也最不该漏的一条**。

## 回头看，真正起作用的是三件事

**1. 把「下一轮必须知道的东西」和「细节」分开存放。**
前者要短到能被读完，后者要全到能被查。

**2. 给每个结论配证据要求。**
`file:line`、来源、可复现的命令。「看起来对」不是证据。

**3. 记录「为什么不是另一个样子」。**
已否决的方案、有意保留的偏移、闸门的盲区 —— 这些是 Agent 无法从代码里推断出来的东西。

至于模型和工具，一直在换。第一版是 codex，后来是 pi，中间还试过别的。

**这三件事一次都没换过。**

## 后记：为什么开始写这个博客

因为这个项目让我意识到，我做的东西和「用 AI 写代码」是两回事。

我真正在搭的是一套**让 Agent 能长期在一个代码库上干活的基础设施**：文档结构、验证闸门、子代理分工、交接机制。

这些东西散在 321 次提交和 14KB 的 `AGENTS.md` 里，没人看得见。

所以开了这个博客。把每个项目的过程、坑和结果摊开写。

翻车的地方写得更细一点，因为那部分我自己回头还要查。
