起因是一个很烦的现象：

> **整个局域网，每隔 30 秒左右，集体断一次。**

不是某台设备，是**所有**设备。看视频卡一下、下载断一下、SSH 掉一下，然后又自己好了。

路由器重启过、光猫换过、网线拔插过。持续了一个月。

## 根因：NAS 的网卡 hang 死

最后定位到的是最不容易怀疑的那一环：

**Synology DS918+ 的板载 Intel I219-V 网卡会偶发 hang 死。**

而它是整个网络的关键路径：

```
小米 AX3000T (192.168.2.1)     主路由，DHCP 在它上面
Oray X1 Pro  (192.168.2.2)     物理旁路由，ImmortalWrt + Clash
Docker 路由  (192.168.2.4)     容器 openwrt，宿主 = NAS
Synology     (192.168.2.6)     NAS，DSM 7.2.1，跑着 14 个容器
```

**关键依赖**：NAS（`.6`）是 Docker 软路由（`.4`）的宿主，通过 macvlan 挂上去。

于是链路变成：

```
客户端 → 网关/DNS = .2 → 透明代理 → .4（在 .6 上）→ 出网
```

**`.6` 一卡，`.4` 的 DNS 和透明代理当场死，所有客户端同时掉线。**

一个月没找到，是因为所有人（包括我）都在怀疑路由器和光猫 —— 谁会怀疑 NAS 的网卡？

## 从"取证"到"运维手册"

项目一开始的定位是**网络风暴取证**：收集证据、定位根因、写报告。

根因找到并缓解之后，我把它**重新定位**了：

> 这不是一个应用代码仓库。它是一套家庭 / 小型办公局域网（`192.168.2.0/24`）的
> **运维手册、工具和证据档案**。

重新定位的依据是：真正需要的能力已经就位了 ——

1. **SSH 公钥访问** NAS 和 Docker 路由容器，免密、可审计
2. **已被验证的 Docker 修复 / 部署经验**（比如恢复过一个页损坏的 MoviePilot `user.db`）
3. **一条可复用的只读采集流水线**（PC ↔ 边缘路由）

历史取证材料全部保留，但它现在降级成了运维的一个子集。

## 访问总线：三条命令

整个仓库的入口收敛成三个脚本：

```bash
./conn.sh nas  '<只读命令>'    # NAS       192.168.2.6:62
./conn.sh owrt '<只读命令>'    # 容器      192.168.2.4:22
./dexec.sh     '<命令>'        # 经 NAS docker exec —— 容器 SSH 不可达时的逃生口
```

`hosts.conf` 是主机清单，`conn.sh` 是统一入口，`dexec.sh` 是逃生口。

认证**只用 SSH 公钥**（`~/.ssh/id_ed25519`，无口令）。密钥指纹记在 `AGENTS.md §8`，**仓库里不存任何密钥材料**。

这三条命令的价值在于：**把"怎么连上去"这件事标准化了**。

之前每次要连 NAS 都要翻笔记找端口（是 62 不是 22）、找用户名、想参数。现在是一条命令。

## 规则：读免费，写要审批

这套规则后来成了我所有运维类项目的模板：

| 规则 | 内容 |
|---|---|
| **远程写操作需逐次审批** | 只读豁免 |
| **环境变量 / 凭据文件需审批** | 仓库内不得出现凭据值 |
| **禁止批量删除** | 只能删明确路径 |
| **绝不裸跑 `fw4 reload`** | 在 `.2` 上会清掉 OpenClash 链 → 客户端失去网络 |

最后一条是血的教训。`fw4 reload` 看起来是个无害的防火墙重载命令，但在那个特定拓扑下，它会**清空 OpenClash 的 nftables 链**，所有走透明代理的客户端当场断网。

> 只读检查是自由的。任何改变状态的操作 —— 无论多小 —— 都要停下来先问。

## 三层文档：规则、设施、过程

```
AGENTS.md      权威规则：审批门、禁令、拓扑、当前处置状态
specs/SPEC.md  仓库总线 —— 每一个标准化的设施：ID、主机、路径、接口、审批、回滚、状态
handoff.md     跨会话账本，append-only
```

三者冲突时 **`AGENTS.md` 赢**。

`SPEC.md` 的"设施总线"是个我很喜欢的设计：**任何标准化过的设施都必须先通过准入条件（C1–C5），然后登记在册。**

一个新设施（比如某个新的采集脚本、某条新的 SSH 通道）如果不登记，它就不存在。这防止了"某个脚本在某次会话里被临时写好、之后就再也没人知道它在哪"。

### handoff 的标签系统

`handoff.md` 是 append-only 的跨会话账本，每行一个事实，带标签：

| 标签 | 含义 | 标签 | 含义 |
|---|---|---|---|
| `[NET]` | 拓扑 / 设备 / MAC / IP | `[DEC]` | 决策 |
| `[SETUP]` | 环境 / 密钥 / 访问方式 | `[ACT]` | 已执行的动作 |
| `[INC]` | 故障现象 / 事件 | `[TODO]` | 待办 |
| `[FACT]` | 已取证事实（有日志/测量支撑） | `[RISK]` | 风险 / 注意事项 |
| `[EXCL]` | **已排除的假设** | `[Q]` | 未解问题 |
| `[FILE]` | 产物文件 | `[PITFALL]` | 踩过的坑 |

**`[EXCL]`（已排除的假设）是最有价值的一个。**

排查网络故障时，你会提出几十个假设，验证掉大部分。如果不记录"哪些已经排除了"，下一个会话（或下一个 agent）会把它们**重新提一遍**。

> `[FACT]` 和 `[EXCL]` 的区别很重要：前者是"这是真的"，后者是"这不是原因"。后者同样值钱。

## 排查过程里的三次认知修正

这是这个项目最真实的部分 —— 我错了三次，每次都记了下来。

### 修正一：故障频率是错的

`§4.5 认知修正（重要）`、`§4.6 历史频率（2026-09-28 取证，已修正）`。

我一开始凭印象估计的"每隔 30 秒"是**错的**。实际取证后的频率分布不一样。

而"链路抖动基线"（`§4.6.1`）是配套的一条：

> **重要，避免误报。**

意思是：网络本来就有一定程度的抖动（正常范围内的丢包、延迟波动）。如果不先建立**基线**，你会把正常抖动当成故障。

### 修正二：Docker / OpenClash 不是故障源

`§4.7 已排除：Docker / OpenClash 是故障源`。

我一度怀疑是 Docker 软路由或 OpenClash 的问题 —— 它们确实在最关键的路径上。验证后排除。

这条进了 `[EXCL]`，省下了后面重新怀疑的时间。

### 修正三：MAC 改写问题

`§4.16` 记录：

> **2026-10-11 换路由 + 新 mesh 后：MAC 改写问题消失，`.2` 完全正常。**

这之前有一个"MAC 改写"的现象一直困扰排查（设备按 MAC 识别，但 MAC 会变）。换硬件之后它自己消失了。

**结论**：那是旧硬件的一个副作用，不是配置问题。追着它查了很久。

## 后来新增的两个判定

排查结束后，这个仓库还在持续记录新的网络现象：

**`§4.14`**（2026-10-04）：**mesh 子路由信号变质 → 主路由载荷加重**。

用户提出的假设：mesh 子路由信号变差时，客户端会改连主路由，导致主路由载荷上升 —— 这看起来像"故障"，其实是**正常的拓扑自适应**。

**`§4.15`**（2026-10-11 定位）：**PC 经中继器接入时「网关指 `.2` 不通、指 `.1` 通」**。

一个很具体的现象，记录下来了。这类"只在某个接入方式下成立"的现象，不记下来根本不可能靠推理得到。

## 独立风险：NAS 全局代理的自引用依赖

`§4.8` 记了一条我自己都没想到的风险：

**NAS 上跑着全局代理，而代理本身又依赖 NAS 上的 Docker 路由。** 一旦 NAS 出问题，它连"自己去查怎么修"的能力都没有（因为出网也要经过那个代理）。

> ⚠️ 这是一个**自引用依赖**：修网络的能力，本身依赖网络。

这条风险没有触发过，但记下来了。因为一旦触发，它会让你在最需要网络的时候失去网络。

## 现在

`net/` 下是网络与路由：报告、防火墙规则、封禁账本、离线包、`clash_drop/`，以及 `net/monitor/`（采集器与巡检）。

`net/monitor/` 的采集器有**轮转标准流程**（`AGENTS.md §9`，硬性）。为什么需要轮转？因为采集器一直跑会把磁盘写满 —— 这类"工具自己变成故障源"的问题，在运维项目里非常常见。

`pc/` 下是工作站侧的诊断（`pc-net.ps1`）、OCR、WSL / pi 文档。

`docker/` 下是容器：`moviepilot/` 的文档与插件笔记、`patches/`。

## 回头看

这个项目不是"写代码"。它是**给一个已经存在的、混乱的、由七八台设备组成的系统，建立一套可操作的秩序**。

具体产出是三样东西：

1. **一条标准化的访问路径**（三条命令，公钥认证）
2. **一套规则**（读免费、写审批、禁止批量删除、不碰某些命令）
3. **一份带标签的事实账本**（含"已排除的假设"）

而它教给我的最重要一条，是那个 `[EXCL]` 标签背后的东西：

> **排查的价值不只在于找到原因，还在于记录下"不是这些原因"。**

一个月的排查里，真正省时间的不是最后的那个答案，而是那些"已经排除了、别再试了"的记录。
