我的音乐库有点规模：

| 歌单 | 内容 |
|---|---|
| 日常杂食 | **3364 首**（流行 / 摇滚 / 日系 / 动漫…） |
| 交响乐 | 卡拉扬 DG & Decca 全集，**3299 轨 / 330 碟** |

问题是它们躺在一个 foobar2000 的歌单里，没有任何结构。而且古典乐的作曲家名字全是德文、英文、各种拼法。

我想做的事很清楚：

1. 按 GENRE 归并大类，出个可视化报告
2. 按 COMPOSER 分组，识别交响曲编号
3. 把作曲家**显示成中文**

## 唯一的硬约束：不许动文件

第一条就把路堵死了一半：

> **不改动任何音频文件**（PT 保种友好）。

我在做 PT 保种。任何对音频文件的写入 —— 哪怕只是改一个标签 —— 都会改变文件哈希，导致**做种失效**。

所以"改标签"这条路从一开始就不存在。

那就只剩一条路：**显示层映射**。

## 显示层映射：Title Formatting

foobar2000 有个叫 **Title Formatting** 的东西：你可以给每一列定义一个格式串，它决定了这一列显示什么。

关键在于：**它只影响显示，不写回文件。**

```
$if($strstr(%genre%,Classical), $replace(%composer%,…), %artist%)
```

这一行读作：如果 genre 里含 "Classical"，就显示替换后的 composer；否则显示 artist。

于是我可以：

- 播放器里看到"卡拉扬"
- 文件标签里还是 `Herbert von Karajan`
- **文件一个字节没变**

但 Title Formatting 是个很古怪的语言。我在上面踩了六个坑。

## 六个坑

### 坑一：整列标题变空 —— 特殊字符未转义

**症状**：粘贴格式串后，**所有**条目（包括不该受影响的歌单）显示为空。

**原因**：搜索串里含有 foobar2000 的**语法字符**，未转义导致**整条格式串解析失败**。

必须转义的字符：

| 字符 | 转义写法 | 说明 |
|---|---|---|
| `,` | `$char(44)` | 函数参数分隔符 |
| `(` | `$char(40)` | 函数调用 / 分组 |
| `)` | `$char(41)` | 同上 |
| `%` | `$char(37)` | 字段引用 |
| `[` | `$char(91)` | 条件括号 |
| `]` | `$char(93)` | 同上 |
| `$` | `$char(36)` | 函数前缀 |

**典型触发**：

```
Symphony no. 3 in D minor (1888/89 Version, Edition Robert Haas)
```

里面的 `(` 和 `,` 都必须转义。

```python
esc_tf('Symphony no. 3 in D minor (1888/89 Version, Edition Robert Haas)')
# → 'Symphony no. 3 in D minor $char(40)1888/89 Version$char(44) Edition Robert Haas$char(41)'
```

**自检方法**：转义后，格式串里除 `$if(` `$replace(` `$strstr(` `$char(` 外**不应再有裸括号**。数一下 `(` 和 `)` 是否相等。

注意失败模式：**一个字符没转义，整条串解析失败，整列变空。** 不是"那一行显示错误"，是**全空**。

### 坑二：`第0交响曲` —— 误用 `$num`

**症状**：用 `$num(%title%,1)` 提取编号，结果全是 `第0交响曲`。

**原因**：`$num(x,y)` 是**"把数字 x 格式化为 y 位（补零）"**，不是"取字符串里第 y 个数字"。

传标题进去 → 解析为数字失败 → `0`。

**正确做法**：不要提取编号，改用**精确前缀映射**（把整段作品名映射成中文）。

这也是我后来所有方案的基调：**不做解析，做查表。**

解析一定会遇到你没预料到的格式；查表只会在遇到新格式时"不匹配"，而不会给出错误答案。

### 坑三：条件判断走反 —— 误用 `$strcmp`

**症状**：用 `$if($strcmp($replace(...),%composer%), A, B)` 判断"是否被替换过"，结果**分支走反**。

**原因**：`$strcmp` 在部分 foobar2000 版本上**返回值语义相反**（相等返回真值）。

**正确做法**：改用语义稳定的 `$strstr`：

```
$if($strstr(%genre%,Classical), <中文作曲家>, %artist%)
```

`$strstr` 找到返回位置（>0，真），找不到返回 0（假）—— 语义稳定，不随版本变。

### 坑四：`$replace` 短串先命中

**症状**：`no. 90` 被当成 `no. 9` 处理。

**原因**：`$replace` 按**给定顺序**依次替换。若 `no. 9` 排在 `no. 90` 前面，会先命中 `no. 90` 的前半段。

**正确做法**：**搜索串按长度降序排列**（长的排前面）。

这条在写映射生成脚本时是自动处理的 —— 又一个"人容易忘、脚本不会忘"的地方。

### 坑五：格式串太长会被拒

**症状**：粘贴后 foobar2000 报错或忽略。

实测的经验值：

| 大小 | 内容 | 结果 |
|---|---|---|
| ~2 KB | 作曲家映射 93 条 | ✅ 正常 |
| ~6 KB | 交响曲前缀映射 101 条 | ✅ 正常 |
| ~20 KB | 专辑级映射 309 条 | ❌ **被拒** |

**做法**：优先用**前缀级映射**（作品名整段），而不是逐条标题映射。仍超限就按卷 / 作曲家拆成多列。

### 坑六：流行歌艺术家变空 —— 映射放错列

**症状**：把 `$replace(%composer%,…)` 放进「艺术家」列后，日常杂食（流行歌**无 composer 标签**）显示为空。

**原因**：该格式串读的是 `%composer%`，流行歌没有这个字段。

这里还有一个更细的陷阱：

> 日常杂食里**有 719 个文件带 COMPOSER 标签**（如 `王菲-主角` 的 composer 是"范炜"）。
>
> 若用「有 composer 就替换」，这些会显示成**作曲者**而非**艺术家**。

**正确做法**（三选一）：

```
① 单独开一列「中文作曲家」:  $if(%composer%, $replace(%composer%,…), )
② 通用艺术家列（带兜底）:    $if($strstr(%genre%,Classical), $replace(%composer%,…), %artist%)
③ 最稳：仅古典走映射，其余一律 %artist%
```

我最后选了 ②。

## cue 乱码：两个误区

古典乐整轨专辑（WAV/FLAC + cue）常见的另一个问题：曲名 / 专辑名乱码。

### 误区一：以为 `fix.exe` 能修

网上流传一个 `fix.exe`。它的说明写着：

```
Usage: %s files(*.wav)
ONLY FOR WAV TAGS EDITED BY FOOBAR2000!!!
```

**它只重写 `.wav` 里的 RIFF INFO 标签。**

而这类专辑的 wav 往往只有 `fmt` + `data`、**没有标签块** —— 所以它无事可做。

> 真正的病根是 **`.cue` 不是 UTF-8**。

### 误区二：改完 cue 就好了

**foobar2000 只从 cue 读一次。**

改完 cue，歌单里还是旧乱码 —— 元数据被**缓存**了（`.fpl` 里存一份 + `metadb.sqlite` 一份）。

必须强制重读：

- 右键 → `Reload info from file(s)`
- 或把专辑删掉重拖
- 或重启 foobar2000

所以我写了个 `fpl_cache_check.py` 来查"哪些歌单条目缓存过期"：

```bash
python scripts/cue_fix.py "D:\Music Backup"              # 体检
python scripts/cue_fix.py --apply "D:\Music Backup"      # 转 UTF-8（逐个 .bak 备份）
python scripts/fpl_cache_check.py --dir "D:\foobar2000"  # 查缓存过期
```

### 实测编码分布

`D:\Music Backup`，2026-09-29：

| 编码 | 数量 |
|---|---|
| utf-8 | 302 |
| utf-8-bom | 149 |
| **GB18030** | 23 |
| **CP1252** | 6 |
| **Big5** | 1 |
| UTF-8 含坏字节 | 2 |
| UTF-16（EAC log，未动） | 39 |

有意思的几个：

- **CP1252**：欧西碟（Rammstein 的 cue 里有 en-dash `–`，在 GBK 里非法）
- **Big5**：港台碟（周杰伦 `Noncompliant.cue`；被当 GBK 读会出现 `㏄狽` 这类 **CJK 兼容区**乱码）
- **UTF-8 含坏字节**：lrc 末尾多 1 个字节，直接丢弃即可

而 `cue_fix.py` 能**自动识别**：含 CJK 兼容区就判为"Big5 被当 GBK"。

## 歌单失效：盘符重映射

**症状**：`Y:\video\Music\…` 全部失效。

排查：

```bash
python scripts/fpl_check.py "<歌单>.fpl"
```

它列出：失效项、按盘符分布、**候选修复盘符**。

本例中的真相：**Y: 实为 X: 的错误映射** —— 64 条失效项全部能在 `X:\video\Music\` 找到（62 条仅盘符错，2 条多一层目录）。

**做法**：

- 同长度替换（`Y:` → `X:`）可以直接改 `.fpl` 二进制
- 若路径长度变化（增删目录层），**不要**原地改 `.fpl`，改为**另存 `.m3u8`**

第二条是关键：`.fpl` 是二进制格式，内部有长度字段。路径变长会破坏结构。

## `.fpl` 与 `.m3u8`

- **`.fpl`** 是二进制，内部以 UTF-8 存 `file://<Windows路径>`，用 `\x00` 结尾提取即可
- **`.m3u8`** 用 UTF-8 写，首行 `#EXTM3U`，每首前可加 `#EXTINF:-1,艺术家 - 标题`

**改盘符优先另存 `.m3u8`** —— 因为它是文本，改起来安全，而且 foobar2000 也读。

## 硬性规则

```
1. 只读 —— 绝不写回音频标签（PT 保种）；文本类修复（cue/log/lrc）也先备份 .bak
2. 禁止批量删除 —— 只能删明确列出的路径
3. 原始歌单先备份 —— 改盘符优先另存 .m3u8
4. Title Formatting 特殊字符必须转义
```

第 1 条是整个项目的地基。它决定了所有方案都必须是**非侵入式**的。

有意思的是，这个约束**反而带来了更好的设计**：

- 显示层映射比改标签**可逆**（删掉格式串就恢复）
- 只读解析比写入**安全**（不会因为脚本 bug 毁掉文件）
- 生成的报告和歌单是**独立产物**，原库不动

## 回头看

这个项目最反直觉的一点是：

> **"不能改文件"这个约束，让方案变好了。**

如果可以随便改标签，我大概会写一堆"读取 → 修改 → 写回"的脚本，然后在某一次误操作里毁掉一批文件（或者毁掉做种）。

因为不能改，所以被逼着往**显示层**和**派生产物**走 —— 而这恰好是更安全、更可逆的方向。

另一个收获是关于 **Title Formatting** 的：它是个没有错误提示的语言。写错了就是"整列变空"，没有任何线索告诉你哪个字符有问题。

对付这类东西，唯一的办法是**在生成端保证正确**（转义函数、长度降序、查表不解析），而不是在消费端调试。
