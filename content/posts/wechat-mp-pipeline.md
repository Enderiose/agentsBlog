第一次想把文章直接发出去，接口回的是：

```
调用失败 /freepublish/submit errcode=48001 api unauthorized
```

账号是认证过的订阅号，但认证在 2025 年被收回了，发布权限跟着一起没了。素材上传、建草稿都还能用，只有「发出去」这一步不行。

于是这个项目的目标当场改写：**不做自动发布，做自动出稿。**

每天 8:00，一条定时任务醒来，挑四条当天的新闻，写四篇 HTML，配好图，上传素材，建一条 4 图文草稿，再写一份审阅文件；8:30，那份审阅文件出现在我的企业微信里。我看一眼，去 `mp.weixin.qq.com` 后台点发表。

## 它是什么

一条内容管线，四个固定位置：

```
[1] 主日报（头条综合）
[2] 模型 / LLM / 智能体
[3] 硬件 / 产品 / 应用
[4] 压轴栏目
```

第 4 位原本是「⚖ 法治观察」（法律、监管、判例）。2026-10-12 被取消了，原话是「由于法律法规经常会接到投诉，取消法律压轴；替代板块增加摇滚乐每日新闻」——所以现在压轴是 `🎸 摇滚乐每日新闻`，选题源换成七家摇滚媒体的 RSS。

整条链上真正「智能」的只有两头：**选题**和**写作**。中间全是硬约束——尺寸必须 1536×591（2.6:1）、封面标题和副标题之间的净间距必须 24px、引用块不许超 300 字、厂商 logo 必须贴右上角。

## 规模

| 指标 | 数值 | 出处 |
|---|---|---|
| 首条测试草稿 | 2026-10-02 23:11 | `drafts_log.jsonl` 第一行 |
| 连续出稿 | 2026-10-03 → 2026-10-12，共 10 天 | `ls -d day_*` = 10 |
| 正文 HTML | 40 篇 | `art{1..4}_*.html` 各 10 个 |
| 审阅文件 | 13 份（10 份日报 + 3 份加更/样稿） | `pending/` 去掉模板 |
| 接口调用记录 | 34 条：draft 10 / multi 12 / update 8 / delete-draft 4 | `drafts_log.jsonl` 统计 |
| 管线代码 | 95 个 `.py`，10645 行 | `find … -name '*.py' \| xargs wc -l` |
| 定时任务 | profile 内共 8 个，本管线相关 4 个 | `cron/jobs.json` |
| 生图通道 | 5 条（songbey > hy > qwen-pro > qwen > zhipu） | `mp_genimg.py` 的 `CHAIN` |

## 三层规则，一条链

```text
/opt/data/mp/                  工作区（脚本 + 素材 + 状态 + 当日产物）
  mp_publish.py                微信接口：check/upload/draft/update/multi/log
  mp_genimg.py                 生图自动链，失败即换下一条，链尾无兜底
  banner_v2.py                 主日报封面：浅色对角渐变底 + 对齐的 logo 墙
  mp_badge.py                  在生图右上角贴厂商官方 logo 角牌
  mp_reuse.py                  sha1 命中就零网络调用地复用素材库 media_id
  hei_font.py                  思源黑体解析：项目卷 → 系统 → 重下 → 兜底
  TOPICS.md / STYLE.md         选什么、怎么画（用户裁定的落地处）
  drafts_log.jsonl             每次 draft/multi/update/delete 的记录
  pending/YYYY-MM-DD.md        每天给人看的审阅文件
  day_2026-10-12/              当日配图
  state/                       巡检状态、prompt 备份、cookie、素材缓存
```

规则分三层，是因为它们被修改的频率完全不同：

- `STYLE.md` —— 视觉规范。改得最勤（24px 间距、logo 摆放、字体、图注格式）。
- `TOPICS.md` —— 选题规范。时效怎么核、判重怎么判、栏目怎么排。
- cron prompt —— 流程步骤。第 0 步探模型链路，第 4 步配图，第 4b 步查引用块字数。

代码里唯一值得抄出来的一段是这个 URL 拼接：

```python
def api(env, path, payload=None, method="POST", files=None, token=None):
    token = token or fetch_token(env)
    sep = "&" if "?" in path else "?"
    url = "%s/%s%saccess_token=%s" % (BASE, path.lstrip("/"), sep, token)
```

微信的接口路径有的自带 `?`（比如 `/material/add_material?type=image`），这时 access_token 必须用 `&` 接。写死成 `?` 的后果是 token 被并进第一个参数值里，报 `41001 access_token missing`——你会去查 token 有没有拿到，其实 token 拿到了，是被 URL 吃掉了。

还有一张把微信错误码翻成人话的表，它承担了大部分排障工作：

```python
ERR_HINTS = {
    40013: "AppID 不正确",
    40125: "AppSecret 不正确 (.env 里 WX_APPSECRET 需填写)",
    40164: "IP 不在白名单 — 去 微信开发者平台(扫码登录)->我的业务->公众号 修改 API IP 白名单",
    40001: "access_token 无效或已过期",
    45004: "摘要(digest)过长 — 缩短到50字内重试",
    48001: "接口权限不足 (账号需已微信认证)",
}
```

## 踩过的坑

### 坑一：随机的 40001 —— 探针把生产凭据顶死了

**现象**：`40001 invalid credential`，一天碰到 3 次。删掉本地 token 缓存重取就好，过一阵又坏。最难查的是它「看起来像过期」——但 2 小时有效期，刚取的 token 不可能过期。

**原因**：微信的 `access_token` 是**全局单例**——任何一次 `/cgi-bin/token` 都会让上一次的失效。我给它加的 IP 白名单巡检每 10 分钟探活一次，每探一次取一个新 token，把出稿脚本缓存的 token 顶死。

**修法**：两个脚本都改用 `POST /cgi-bin/stable_token`（`force_refresh:false`，重复调用返回同一个 token）。

**教训**：探针不是免费的。写巡检之前先问一句：这个探针会不会消耗或顶掉生产要用的资源？同一天我还犯了另一次同类的错——为了确认生图站的模型 id，连着真出图探测，一次烧掉十条额度（10 次真实生图里 7 次是探测），被当场指出。

### 坑二：40164 —— 出口 IP 变了，而白名单没有 API

**现象**：`upload` 和 `draft` 全部被拦，`errmsg` 里带 `invalid ip`。换过路由之后必现。

**原因**：容器出口 IP 会变，而 API IP 白名单只能在微信开发者平台网页扫码改，**没有开放 API**。

**修法**：无损探测。用**真实 AppID + 假 secret** 调 `/token`，40164 的 `errmsg` 会原样回显微信看到的那个 IP——不需要真 secret，也不会产生有效 token：

```python
        m = re.search(r"invalid ip ([0-9a-f.:]+)", d.get("errmsg", ""))
        if m:
            extra = "\n微信看到的本机出口 IP = %s —— 把它加入白名单即可" % m.group(1)
```

外面再挂一个每 10 分钟一次的巡检，变了就往企业微信推一条告警，附后台链接。

**教训**：没有 API 的地方，至少要把人工步骤压缩成一条可执行提示。报错里回显的 IP 就是微信替我测出来的——它比我更清楚我长什么样。

### 坑三：报错码指的地方，往往不是错的地方

**现象 A**：摘要过长报 `45004 description size out of limit`。

**原因**：文档没写 digest 的字数上限。实测 83 字失败、57 字（109 字节）通过。

**修法**：摘要控制在 50 字内；脚本命中 45004 就提示「缩短重试」。

**现象 B**：改一条已经建好的多图文草稿，报 `40007 invalid media_id`。

**原因**：`/draft/update` 的字段名是 `articles`（对象），不是 `article`。报错说的却是 media_id 无效。

**修法**：字段名改成 `articles`，并支持 `--index N` 只改第 N 篇——多图文草稿不能靠重跑 `multi` 来改内容，那会建出第二个草稿。

**教训**：微信的 errcode 回答的是「哪一类错」，不是「哪里错」。40007 让你去查 media_id，实际错在字段名。这张错误码表的每一行，都是被误导过一次换来的。

### 坑四：满屏乱码 —— 两处编码，两个方向，一真一假

**现象**：用户在后台看到正文里是 `\u8c37\u6b4c` 这种字面量；我用脚本回读草稿时，看到的却是 `æ¥æ¥`。

**原因**：两个独立的坑叠在一起。① **发送**时 `requests(json=payload)` 默认转义成 `\uXXXX`，微信按字面量原样存储——`draft/add` 的文档明确警告过这一点；② **读取**时微信返回 `Content-Type: text/plain` 且不带 charset，requests 按 ISO-8859-1 解码，中文全变乱码。

**修法**：

```python
        # 必须用 ensure_ascii=False 发原始 UTF-8 中文
        body = json.dumps(payload or {}, ensure_ascii=False).encode("utf-8")
        r = requests.post(url, data=body,
                          headers={"Content-Type": "application/json"}, timeout=60)
```

```python
    # 响应头是 text/plain 无 charset, requests 会按 ISO-8859-1 解码 → 中文乱码, 强制 UTF-8
    d = json.loads(r.content.decode("utf-8"))
```

**教训**：第二个坑只影响显示——**存储其实是对的**。我当时差点据此把一篇正确的稿子重发一遍。看到乱码先分清是「存坏了」还是「解码坏了」，再动手。

### 坑五：字体静默降级 —— 容器重建后，图里的字悄悄换了

**现象**：用户一眼看出封面「又用了旧字体」。我看代码没报错，看图也分不出。

**原因**：容器重建会清掉镜像层的 `/usr/share/fonts/`。旧写法是 `if not os.path.exists(FP): FP = wqy-zenhei.ttc`——路径没了就**静默**回退到文泉驿正黑，一行日志都不打。

**修法**：字体真身放进项目卷 `/opt/data/mp/fonts/`（思源黑体三个字重，共 24.6 MB），`hei_font.py` 按「项目卷 → 系统目录 → 自动重下 →（全挂才）wqy + stderr 警告」的顺序解析，画字脚本一律 `from hei_font import FP, FP_BOLD`。自检脚本跑一下，输出必须指向项目卷。

**教训**：`if 找不到: 用默认值` 是给用户看的 bug。降级可以，但降级必须留痕。

### 坑六：200 + HTML —— 状态码说成功，内容是首页

**现象**：生图请求返回 HTTP 200，`r.json()` 要么抛异常，要么被当成成功。

**原因**：转售站在故障时会用 200 包一层**站点首页 HTML**。同一时期另一个通道的上游故障是秒回 `500 do_request_failed`，还有一个是 Cloudflare `524` 超时 125 秒——三种失败，三种完全不同的表现。

**修法**：定死一条规矩——**200 但非 JSON，一律判为通道故障**，直接换下一条通道。这条规则后来在微信侧也复用了：所有接口响应都强制 `r.content.decode("utf-8")` 后再解析，非 JSON 直接 `die`。

**教训**：判断成功要看内容契约，不要看状态码。现在这条链的末尾没有兜底：五条生图通道全挂就报错退出，不降级合成——因为「悄悄合成一张扁平图交上去」比失败更贵（踩过一次，三张 1.5:1 的合成图被当成另一个通道出的）。

### 坑七：`$(cat file)` 把整轮规则清空了

**现象**：改 cron 任务的 prompt 之后，任务的规则整段消失，但 CLI 照样打印 `Updated`。

**原因**：我用的是 `hermes cron edit <id> --prompt "$(cat file)"`。上一步生成 `file` 的命令因为断言没过失败了，文件不存在，`$(cat ...)` 展开成**空串**——prompt 被静默清空。

**修法**：① 改动一律走 Python API（`use_cron_store(HOME)` → `update_job`），不经过命令行参数；② 改之前 `assert prompt.count(anchor) == 1` 确认锚点唯一，并把文件长度打出来核对；③ **改完立刻 `cp` 一份到 `state/daily_prompt_backup_<date>.txt`**。

那天是靠重放当天的编辑脚本、从 `cron/output/<job>/<时间戳>.md` 里捞出 prompt 快照才还原的（6583 字 → 8471 字）。

**教训**：任何「把文件内容塞进命令行参数」的写法，都有一个「文件不存在 = 空值」的静默失败模式，而且它不会报错。文件内容进命令行之前，先检查它非空。

## 现状与欠债

**发布仍然是人工的。** `freepublish` 是 48001，草稿箱到「已发表」之间还有三个手点：合集归组、原创声明、创作来源（「内容由 AI 生成」）。2026-10 查遍订阅号 API 目录确认过，这三项都没有服务端接口。等账号重新认证之后才谈得上自动发布。

**音频插不进去。** `<mpvoice>`（含空标签）被 `draft/add` 直接拒（`45166 invalid content`）、`<audio>`/`<iframe>` 被静默剥掉、`<qqmusic>` 虽然原样保留但渲染不可控。所以正文里只能放一个橙色虚线占位框标出插入点，把曲目、搜索词、是否 VIP、免费替代列在审阅文件里，由人后台手插。更麻烦的是 `draft/add` 会**整段删掉 HTML 注释**（回读 0 处）——连「用注释做标记」这条退路都没有。

**素材库无法枚举。** `material/batchget`、`get_material_count`、`get_groups` 在这个账号上全部回 `40066 invalid url`，只能按 media_id 单个取。名称和 media_id 的对应关系，完全靠本地 `.state/reuse/<name>.json` 登记。

**白名单还是人工的。** cookie 通道那个「自动写入白名单」的脚本，写入接口一直没定稿，所以现在的流程是：巡检发现 IP 变了 → 推企微告警 → 人去后台换。

**判重靠本地账本。** `freepublish/batchget` 同样 48001，读不到账号已发布的列表，只能翻 `drafts_log.jsonl` + `pending/*.md` + 人工反馈。这套判重规则是被一次事故逼出来的：某天的第 2 篇写了某个模型的跑分差距，被判重删稿、当天只发 3 篇——**「文章是今天发的」不等于「事件是新的」**。

**两处副本会漂移。** 脚本在 `/opt/data/mp/` 和 profile 的 `scripts/` 各有一份，约定是「改完 `cp` 过去」。实际量了一下：18 个同名脚本里 15 个 md5 一致，**3 个不一致**——`mp_publish.py`、`mp_ip_guard.py`、`mp_qr_login.py`，恰好是最关键的三个。其中 `mp_publish.py` 的差异就是坑一里的 `stable_token` 改造只落到了运行副本上。靠人肉同步的约定，早晚会欠账。

**规则随时会被推翻。** 法律压轴那一块（4 张封面按日轮换、判例写法、素材溯源）刚做熟，2026-10-12 就因为「经常会接到投诉」整体取消，换成摇滚乐新闻源。前一天的规范文件，第二天就是历史——这也是为什么规则要和代码分开写。

## 回头看

**一、「自动发布」不是技术问题。** 我一开始以为任务是把 `freepublish` 调通，实际是账号的认证被收回了——接口权限不会因为代码写得好而恢复。想清楚一件事的边界在哪，比把它做完美更省时间。这条边界一画出来，整个项目的形态就变了：从「自动发文机器人」变成「一个每天准时把稿子准备好、等我点头的人」。

**二、探针会破坏生产。** token 是全局单例、生图是按张计费的——「只是测一下」的调用会消耗真实资源。巡检脚本、模型探测、通道验证，都要先想清楚代价。

**三、静默降级比报错贵。** 字体悄悄换成文泉驿、requests 悄悄按 ISO-8859-1 解码、`$(cat file)` 悄悄展开成空串、200 + HTML 悄悄当成成功——这四件事的共同点是：**没报错，但错了**。现在这条链上的规矩是，任何降级都要留痕：要么打日志，要么写进当天给人看的审阅文件。

**四、报错码不等于原因。** 40007 说 media_id 无效，其实是字段名错；40001 说 token 过期，其实是别的脚本刚取了新 token。每次被误导，就往错误码表里补一行。

**五、规则要写在会被读到的地方。** 用户的裁定分散在 `STYLE.md`、`TOPICS.md`、cron prompt 和技能文档四处。只改一处，第二天就会被退回。所以现在每落地一条裁定，都要同时改三处，并备份一份 prompt。

最省事的结论是：**把「每天的判断」和「每天的纪律」分开**。判断交给模型（今天写哪四条、怎么起标题），纪律写成代码和规范（尺寸、间距、字数、颜色、logo 位置）。判断错一次，改一条选题规则；纪律松一次，就要花一整天去查一张图为什么变了。
