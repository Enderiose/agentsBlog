需求很实际：

我的机器上装着 WorkBuddy / CodeBuddy，里面有托管模型（`deepseek-v4.1-flash`、`hy3` 系列）。我想让**本机其它程序**也能调这些模型 —— 用一个标准的 OpenAI 兼容接口。

难点只有一个：**鉴权怎么办？**

## 两条路，我选了难的那条

### 路线 A：抓凭据（我没走）

最直接的做法：

1. 找到客户端存凭据的地方
2. 读出来
3. 拿着它直接调上游 API

**这条路我一开始就否掉了。**

原因不是技术难度，是**边界**：

- 凭据一旦被我读进内存，它就进入了我的日志、我的错误信息、我的进程环境
- "只是读一下"是个滑坡 —— 下一步就是"只是缓存一下"，再下一步就是"写进配置文件方便调试"
- 而且它**违反了我所有项目里的那条规则**：凭据值不进上下文

### 路线 B：让 CLI 自己鉴权（我走的）

```bash
node <WorkBuddy>/cli/dist/codebuddy-headless.js \
  -p "<prompt>" --model <model> --tools "" --output-format json
```

**每个 API 请求 spawn 一个 CLI 无头进程**，由 CLI 自己用它**已登录的会话**完成鉴权。

于是：

> 不抓包、不扒 token、**不转发任何凭据**。

中转服务从头到尾不知道凭据长什么样。它只知道"把 prompt 交给 CLI，拿回结果"。

## 代价：一个必须说清楚的边界

这个设计带来一个硬约束：

> **本服务必须在沙箱外、以当前登录用户的身份运行。**

在 WorkBuddy 的沙箱会话里跑，CLI 读不到 `CodeBuddyExtension/Data/Public/auth/`，会报：

```
Authentication required
```

**这是沙箱的既定边界，不是 bug。**

README 里写得很直白 —— 因为不写清楚，用户（包括未来的我）会以为是服务写错了。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/health` | 健康检查，**不需要鉴权** |
| GET | `/v1/models` | 列出白名单内的模型 |
| POST | `/v1/chat/completions` | 对话补全，支持 `stream: true` |

除 `/health` 外都需要 `Authorization: Bearer <key>`。

**`/health` 免鉴权**是刻意的：健康检查要能被监控系统调用，而监控系统不该持有 key。

## 模型白名单：默认拒绝

`config.json` 的 `models` 是**对外模型名 → CLI 实际模型 ID** 的映射：

```json
{
  "deepseek-v4.1-flash": "deepseek-v4.1-flash",
  "hy3": "hy3-free",
  "hy3-free": "hy3-free",
  "hy3-preview-agent": "hy3-preview-agent"
}
```

> **不在表里的模型名一律返回 404，永远不会被转发。**

这是个安全设计：**默认拒绝**。想加模型必须显式写进配置。

如果反过来（"默认允许，黑名单拒绝"），那么任何一个新出现的模型名都会被自动转发出去 —— 而你可能根本不知道它存在。

## 四条安全须知

README 里这四条我标成"重要"，因为它们都是"配错了会出大事"的类型。

### 1. `disableTools` 保持 `true`

**这是最关键的一条。**

CodeBuddy CLI 默认带一整套**文件读写 / 命令执行**工具。

一旦放开，**任何能访问本服务的人都可以通过 prompt 在你机器上执行命令**。

```json
{ "disableTools": true }
```

默认已禁用，没有特别理由不要改。

### 2. 默认只听 `127.0.0.1`

改成 `0.0.0.0` 会把接口暴露到局域网（甚至公网，取决于你的网络）。

要暴露时：

- 先换一把强 key
- 确认 Windows 防火墙规则是你**有意**加的
- **别把端口映射到公网**

### 3. key 是明文存在 `config.json` 里的

**别把这个文件提交到 git。**

这条在 README 里是加粗的 —— 因为 `config.json` 是首次启动自动生成的，很容易顺手 `git add .`。

### 4. 走的是你账号的额度

对外提供服务前想清楚用量。

## 零依赖，单文件

```
relay.mjs        主服务（单文件，零依赖）
config.json      配置，首次启动自动生成
start.cmd        Windows 启动脚本
logs/            运行日志（按天切分）
```

**代码里没有任何硬编码路径**：

- `config.json` 和 `logs/` 跟着脚本自身位置走
- CLI 路径按 `LOCALAPPDATA` 自动探测
- CLI 的工作目录用系统临时目录

所以整个目录搬到哪个盘都能直接跑。

这条约束是刻意的 —— 我在其它项目里被"写死路径"坑过太多次，尤其是 Windows 上盘符会变。

## 已知限制：诚实清单

这是我认为 README 里最有价值的一节。**所有限制都写出来了，不藏着。**

### 不是真流式

CLI 的输出格式决定了 relay 只能做到**增量转发** —— 拿到 CLI 的文本增量就立刻吐给客户端。

但首字节延迟比真流式高（要等 CLI 冷启动，约 1–3 秒）。

**用户会感觉"卡了一下才开始出字"。**

### 每次请求冷启动一个 CLI 进程

单请求开销约 1–3 秒，比直连 API 慢。

> 适合低频调用，不适合高 QPS 场景。

`maxConcurrency` 控制并发上限（默认 4），超了会排队。

### 多轮对话是"拍平"的

OpenAI 的 `messages` 数组会被**渲染成一段对话记录**交给 CLI，而不是复用服务端会话。

所以 `tool` 消息、函数调用这些高级特性**不支持**。

### 不是纯 completion

底层是 agent，**回答风格会带一点 agent 味**。

这条很微妙 —— 你问一个简单问题，得到的回答可能带着"让我先看看…"这种 agent 腔调。

### 图片输入会被丢弃

`image_url` 被替换为 `[image omitted]`。

## 另一个选择：自带 key 的直连反代

README 里我专门写了一节对比，因为**方案 B 不是所有场景下都最优**：

| | 本方案（CLI 包装） | 自带 key 直连 |
|---|---|---|
| 需要额外付费 | **否**，用现有额度 | 是 |
| 速度 | 每次冷启动 1–3s | 直连，快 |
| 真流式 | 否 | 是 |
| 稳定性 | 依赖 CLI 版本 | 高 |
| 支持 function calling | 否 | 是 |

如果你手上有 DeepSeek 官方 key 和腾讯混元 key，**直连反代更简单、更快、也更稳** —— 不需要 CLI，写个纯 HTTP 转发就行。

我把这段写进 README，是因为：

> **一个方案的价值取决于约束。** 不说清"它在什么情况下不是最优解"，用户就没法做判断。

这个项目的约束是"不想额外付费、用现有额度"。**脱离这个约束，它就不成立。**

## 配置项

| 字段 | 默认 | 说明 |
|---|---|---|
| `host` | `127.0.0.1` | 监听地址 |
| `port` | `8787` | 端口 |
| `apiKeys` | 自动生成 | 允许的 key 列表，可放多把 |
| `models` | 见上 | 模型白名单 |
| `cliPath` | 自动探测 | CLI 入口，探测失败时手动指定 |
| `requestTimeoutMs` | `300000` | 单请求超时 |
| `maxConcurrency` | `4` | 同时最多几个 CLI 进程 |
| `disableTools` | `true` | **禁用 CLI 全部内置工具** |
| `extraCliArgs` | `[]` | 追加给 CLI 的参数 |
| `workDir` | 临时目录 | CLI 的工作目录 |

环境变量可临时覆盖：`RELAY_HOST`、`RELAY_PORT`、`RELAY_CLI`、`RELAY_CONFIG`。

## 回头看

这个项目最值得说的不是"我做了个中转"，而是**我选择不做的那件事**。

抓 token 是可行的，甚至更简单、更快。但它会：

- 把凭据带进一个我自己写的进程
- 让"凭据不进上下文"这条规则出现例外
- 建立一个坏先例 —— 下一个项目会更容易妥协

而选另一条路的代价，只是**慢 1–3 秒**。

> **当你面前有一条"更快但需要碰凭据"的路，值得先问一句：这个快，值多少？**

在这个场景里，答案是不值。这是个本机低频调用工具，不是高并发服务。
